# 代码编写规范

> 适用项目：fons4cloud
> 规则状态：已确认
> 更新日期：2026-08-13
> 依据来源：用户确认、`AGENTS.md`、`.specify/memory/index.md`、根 `pom.xml`、代表性源码和测试

## 基本原则

- 修改代码前必须先理解需求、阅读相关上下文，并确认影响范围。
- 新增代码和发生实质修改的相关代码采用“声明式入口校验 + 行为型实体 + 同域聚合根 + 领域服务决策 + 应用层业务编排 + 基础设施技术运行编排”。
- 本规范优先于历史源码习惯和旧示例，但不要求立即迁移全部存量代码。
- 优先遵循项目规范、知识库、现有模块分层和已有代码风格。
- 优先复用已有代码，不重复创建已有工具类、公共模型、异常、转换器、Facade、Provider、Adapter、AutoConfiguration 或 Starter。
- 不允许修改与当前需求无关的代码、配置、测试、知识库或规则文件。
- 不允许引入新的技术框架，除非用户明确确认且已有项目技术栈无法满足需求。
- 不允许删除核心业务逻辑、公共能力骨架、接口契约或已验证知识。
- 不允许修改数据库结构，除非需求明确要求并经过用户确认。
- 不得编造接口、编造数据库字段、编造第三方 API、编造生产配置或编造业务流程。
- 公共契约、持久化结构、鉴权链路、网关路由、MQ 抽象、Token 生命周期等高影响变更必须先说明兼容性、回滚和验证方式。

## 工具类与复用

- 无 Bean 注入、无外部资源访问、无业务状态的纯工具类放 `common.util`。
- 依赖 Spring Bean、配置、数据库、Redis、MQ、文件、远程接口或包含领域判断、状态迁移的能力不得放入 `common.util`。
- 常见工具使用优先级：Apache Commons → fons4cloud 现有工具/组件 → Hutool 等专项能力 → 确认无可复用能力后新增工具类。
- 字符串判空优先 `StringUtils.isBlank/isNotBlank`；集合判空优先 `CollectionUtils.isEmpty/isNotEmpty`；Map 判空优先 `MapUtils.isEmpty/isNotEmpty`；数组操作优先 `ArrayUtils`。
- 构造器不变量允许使用 `Objects.requireNonNull`；不为形式统一过度包装简单对象判断。
- Hutool 可用于日期、转换、缓存、JSON 等既有专项能力，不全面禁止；同一模块同类功能避免 Apache Commons、Spring Utils 与 Hutool 混用。
- 不为单次简单调用强行引入新依赖；需要的 Commons 模块应由依赖链提供或在模块 POM 中明确声明。
- 通用返回优先使用 `R<T>`、`ResultCode` 和已有 `Result` 体系，不新增平行返回模型。
- 业务异常优先使用 `BizException` 及现有领域异常，例如 `AuthException`、`RedisException`、`DistributeLockException`、`MqTransactionalException`。
- 对象转换优先使用已有 MapStruct Converter 和 `CommonConverter`，不手写重复字段搬运逻辑。
- 新增 5 个以上字段映射或重复出现同类字段搬运时，优先复用或新增 MapStruct Converter、`CommonConverter` 或项目既有转换器；不使用转换器必须在实施报告中说明原因。
- 数据访问优先使用已有 MyBatis-Plus Mapper、BaseMapper、公共 Mapper 和自动配置。
- ID、缓存、Redis、加密、并发、JSON、日期等能力优先复用 `fons4cloud-common-*` 中已有工具和组件。
- 新增能力适配时优先复用项目已有公共抽象；只有确有差异时才新增 Provider、Adapter、Client 或 Template。
- 新增配置应优先放入已有配置模型或 AutoConfiguration 模式，不散落硬编码。

## 代码风格

- Java 源码保持 UTF-8 编码，遵循当前 Maven JDK 21 配置。
- 包名、类名、方法名、字段名必须表达职责，不使用临时、含糊或与现有语义冲突的命名。
- 注释只写关键逻辑、类字段含义、接口契约、异常分支和非显而易见的设计原因。
- 新增公共类、公共方法、配置类、接口和关键字段必须补充简洁 JavaDoc 或字段注释。
- 使用 Lombok 时遵循现有模式，不在实体和复杂领域对象上滥用会隐藏关键行为的注解。
- 常量、状态、错误码、授权模式、资源类型等固定语义优先使用枚举或已有常量类。
- 实体不使用 `Entity` 后缀；聚合根统一使用 `Aggregate` 后缀。
- 状态、类型和原因码优先放 `common.constants.<domain>`；状态枚举只表达稳定值、编码和说明，不执行状态迁移、查询或外部调用。
- 不在业务逻辑中硬编码魔法值；必须落入常量、配置项或已确认规则。
- 不把 target、generated-sources、构建产物或临时文件作为人工修改对象。

## DDD-lite 编码约束

- 采用横向技术分层：`controller`、`application`、`common`、`domain.entity`、`domain.mapper`、`domain.service`、`infrastructure`；复杂业务按领域增加二级包。
- 依赖方向为 `controller → application → domain`、`application → infrastructure`、`domain.service → domain.mapper`。
- Controller 负责协议适配、声明式校验和调用 Application，不承担业务编排。
- Application 负责跨领域业务用例、多个 Domain Service 协作、Infrastructure 调用、事务、幂等、补偿和执行顺序。
- Domain 负责业务合法性、实体行为、聚合一致性和领域策略。
- Infrastructure 负责框架集成、外部系统和技术运行编排，不决定业务结论。

### 行为型实体

- Entity 可以封装初始化、恢复后校验、数据变化、局部判断、状态判断、状态迁移和自身不变量。
- Entity 不得注入 Bean、查询 Mapper、调用数据库、缓存、MQ、Agent、文件或远程服务，不得管理事务或编排跨领域流程。
- 外部不得通过 Setter 绕过 Entity 行为修改复杂状态。

### 聚合根

- Aggregate 管理同一领域、同一一致性边界内的多个 Entity，对外提供统一操作入口并维护跨实体不变量。
- 内部 Entity 继续负责局部规则；Aggregate 必须调用实体行为，不直接绕过实体修改字段。
- 外部不得绕过 Aggregate 修改受一致性保护的内部实体。
- Aggregate 不得包含其他领域的可变实体，不得查询 Mapper、调用外部服务、承担跨领域编排或无限扩大边界。
- 跨领域使用标识、不可变 Snapshot、Context、Result 或领域事件协作。

### Domain Service、Application 与 Infrastructure

- Domain Service 可以注入本领域 Mapper，查询和保存本领域 Entity，装配或恢复 Aggregate，执行同领域复杂判断和策略选择。
- Domain Service 不得查询其他领域 Mapper，不得调用远程服务、MQ、Redis、Agent或文件服务，不得重复 Entity/Aggregate 已有规则。
- Application 不得重复 Request 注解已覆盖的简单校验，不得通过 Setter 修改 Entity，不得复制状态机或堆积应归属 Domain 的复杂判断。
- Infrastructure 可以编排缓存、锁、MQ、远程调用、文件、搜索、Agent、线程、重试、超时和熔断等技术步骤。
- Infrastructure 不得判断业务状态是否合法，不得作出审批、发布、完成等业务结论，不得编排跨领域业务顺序或直接修改领域实体状态。
- Infrastructure 编排技术能力，Application 编排业务能力，Domain 判断业务合法性。

### 持久化

- 简单 Entity 可以携带最小 MyBatis 映射注解；映射注解只表达表和字段，不得出现 Mapper、Wrapper、SQL 构造、事务或基础设施调用。
- 复杂聚合在 `domain.entity.<domain>` 中放 Entity 和 `XxxAggregate`；Mapper 查询实体，Domain Service 装配 Aggregate。
- Aggregate 完成行为后，由 Domain Service 使用本领域 Mapper 保存变化实体；Aggregate 不要求直接映射到单表。
- 不强制所有场景完全分离领域对象和持久化对象；确需分离时必须提供明确转换边界。
- Request、Response、DTO、VO 不得兼任持久化实体。

- Facade、Provider、Adapter、Repository、Mapper 的职责必须单一，不在基础设施适配类中写跨领域业务编排。
- 新增能力域或适配对象时，先查 `.specify/memory/capabilities/` 中是否已有公共骨架和标准判定。
- 单个实现不得被写成全项目标准；新抽象必须来自复用需求、横向差异或用户确认。

## API 接口设计

- 所有外部入口必须在调用 Application 前优先使用 Jakarta Validation。
- HTTP Request 字段使用 `@NotNull`、`@NotBlank`、`@Size`、`@Pattern` 和数值范围等约束，Controller 参数使用 `@Valid`。
- `PathVariable`、`RequestParam` 和方法参数约束由 Controller 配合 `@Validated` 触发。
- RPC/Facade Request 复用 Jakarta Validation 约束，由 RPC Filter 或统一 `BeanValidator` 触发。
- MQ、任务和事件入口由 Adapter 在进入 Application 前触发校验。
- 嵌套对象和集合元素使用级联 `@Valid`；配置对象使用 `@Validated`。
- 校验异常交给全局异常处理并统一返回 `R` 和参数错误码，Controller 不重复捕获。
- 必填、空值、长度、格式、范围、数量和嵌套结构由 Request 与入口层负责；数据唯一性、权限、幂等和外部状态由 Application 或 Domain Service 负责；实体不变量、聚合一致性和状态迁移由 Entity 或 Aggregate 负责。
- Application 禁止重复编写注解已经覆盖的简单判空和格式判断。
- 纯请求结构的跨字段约束可以使用类级 Validator；依赖数据库、权限、领域状态或外部调用的规则不得伪装成参数注解。
- 创建、修改、查询语义明显不同时，优先拆分 `XxxCreateRequest`、`XxxUpdateRequest`、`XxxQueryRequest`；字段和约束高度一致时才使用 Validation Groups。
- HTTP API 返回优先使用统一 `R<T>` 结构；RPC Facade 也应遵循已有返回模型和错误码习惯。
- `common` 可按语义使用 `model`、`request`、`response`、`dto`、`vo`、`util`；内部跨层对象优先 `model`，HTTP 输入优先 `request`，HTTP 输出优先 `response`。
- RPC和复杂集成对象可以使用 DTO，页面视图对象可以使用 VO；一个类型不得同时兼任 Request、Response、Entity 和持久化模型。
- 公共类、公共方法、接口方法、Request、Response 和关键字段必须写清楚语义、边界、单位、状态口径和兼容性影响。
- 安全、权限、Token、密钥、状态、时间、ID、外部资源引用等字段必须写明来源、格式、有效范围和不可误用边界。
- API 入参、出参、Header、PathVariable、RequestParam 必须有明确语义，不能用未确认字段承载多种含义。
- 安全相关接口必须明确认证、授权、白名单、Token、用户上下文和异常返回语义。
- 网关与下游之间的认证用户传递必须遵循已有 `AUTH_USER` 头约定，不允许客户端伪造该头。
- Token 生成、刷新、吊销、内省和权限校验必须遵循授权服务能力边界，不得在网关或业务模块重复实现。
- 对外接口变更必须说明兼容性；删除字段、修改字段语义、修改状态码或修改错误码前必须确认。
- 不得把测试样例、配置样例或单个调用方参数写成通用 API 标准。

## 异常与日志

- 可预期业务失败使用业务异常和结果码表达，不使用裸 `RuntimeException` 或字符串错误散落。
- 系统异常必须保留 cause，日志中记录可定位信息，但不得泄露 token、密码、clientSecret、身份证、手机号、邮箱、连接串等敏感数据。
- 鉴权失败、无权限、非法请求、限流等安全事件必须保持统一错误结构，不随意返回堆栈或内部实现细节。
- 日志不得输出完整请求体、完整敏感对象或未经脱敏的外部流水；需要排查时只输出必要摘要、ID、状态和错误码。
- 异常处理不得吞掉影响一致性的失败；确需降级时必须有清晰日志和返回语义。
- 禁止把调试日志、临时代码、`System.out.println`、硬编码测试账号提交到正式源码。

## 数据映射与安全

- 字段映射必须基于实体、Mapper、XML、正式 SQL 或已确认文档，不得编造数据库字段。
- 金额单位必须在字段、DTO、接口或文档中明确；未确认单位时不得默认分、元或其他口径。
- 日期时间字段必须明确时区、精度和格式；跨服务接口不得隐式转换日期口径。
- 状态字段必须使用已有枚举或已确认状态机；不得用裸字符串或未登记数字状态扩展语义。
- 外部流水号、业务流水号、消息 ID、Token、路由 ID 等唯一标识必须明确来源、唯一性和幂等口径。
- 敏感数据必须遵循已有加密和脱敏模式；例如实名、身份证等字段已存在 AES TypeHandler 处理时，不得绕过。
- 日志脱敏、加密、权限和审计必须作为编码约束处理，不得在实现完成后再补。
- 权限和审计相关数据必须保留操作者、资源、操作、结果、错误码等必要信息，不得只记录自由文本。

## 数据访问与事务

- 数据访问优先使用已有 Mapper、MyBatis-Plus 配置、公共实体和公共自动填充能力。
- Domain Service 只使用本领域 Mapper；跨领域数据由 Application 通过对应领域服务获取。
- 事务边界必须放在应用服务或明确的事务服务中；跨数据库、MQ、Redis、外部服务的一致性必须说明补偿或失败处理。
- 更新、删除、批量操作必须具备条件约束；不得绕过防全表更新与删除保护。

## DDL与迁移脚本

- 涉及 DDL 或迁移脚本时，表注释、字段注释、脚本说明默认使用中文，便于审查和长期维护。
- DDL 必须包含审查清单：表注释、字段注释、主键策略、非空约束、默认值、索引设计依据、兼容性影响、回滚说明。
- 索引设计必须克制；非唯一索引必须绑定明确查询、排序、关联、唯一性或运维审计场景，不得按字段清单机械建索引。
- 新增、删除或修改表结构前必须先确认需求、数据迁移、回滚方式和影响范围。
- 未有正式 SQL、实体/Mapper 证据或用户确认时，不得反推表结构或字段类型。

## 测试与验证

- Request 校验测试必须覆盖空值、长度、格式、嵌套对象、集合元素和边界值，并确认非法输入未进入 Application。
- Entity/Aggregate 测试覆盖合法迁移、非法迁移、局部不变量和跨实体一致性。
- Domain Service 测试覆盖本领域实体查询、聚合装配、业务判断和持久化结果。
- Application 测试覆盖跨领域顺序、事务、幂等、补偿和技术能力失败。
- Infrastructure 测试覆盖技术协议、超时、重试和适配，不以技术测试替代领域规则测试。
- 新增或修改公共抽象、鉴权、网关、MQ、缓存、数据库、分布式锁、限流、事务、文件存储等高风险能力时，必须补充或更新测试。
- 测试应覆盖成功路径、关键失败路径、边界条件和兼容性影响。
- 单元测试命名应表达行为，例如 `shouldCreateSuccessRelease`、`shouldCreateFailedAuditRecord`。
- 变更 Maven 模块、依赖、AutoConfiguration、公共 API 或序列化格式时，必须至少运行相关模块测试或说明无法运行原因。
- 文档和规则变更必须运行对应技能校验脚本；校验失败必须修复后再交付。
- 不得只依赖人工阅读作为高风险代码变更的唯一验证方式。

## 禁止事项

- 禁止在 Application 重复 Request 注解已经覆盖的简单参数校验。
- 禁止通过 Setter 绕过 Entity/Aggregate 行为修改状态。
- 禁止 Domain Service 查询其他领域 Mapper 或调用外部技术能力。
- 禁止 Infrastructure 决定业务状态、业务结论或跨领域业务顺序。
- 禁止 Aggregate 包含其他领域的可变实体、调用 Mapper 或外部服务。
- 禁止把有 Bean 注入、外部访问或业务规则的类型放入 `common.util`。
- 禁止未经确认新增数据库表、字段、索引、DDL、迁移脚本或修改已有表结构。
- 禁止绕过已有认证、授权、Token、权限资源、白名单、限流、审计和加密机制。
- 禁止新增与现有 `R<T>`、异常、转换器、Mapper、配置模型并行的重复体系。
- 禁止在公共模块引入与项目技术栈不一致的新框架或重量级依赖。
- 禁止在源码、配置、测试、日志或文档中提交真实密钥、token、账号、连接串、身份证、手机号、邮箱等敏感信息。
- 禁止修改生成代码、构建产物、缓存目录或与当前需求无关的文件。
- 禁止用单个实现、单个配置样例或单个测试用例推导全项目标准。
- 禁止在未说明验证结果的情况下交付代码变更。
